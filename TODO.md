### Why a foil profile prints yellow (measured on a simulated press + scanner)

**The plan is `docs/calibration.md`** — nine stages: metric, then chart, then what the chart makes possible. The items below are the findings it is built from.

- [x] **All nine stages built, and the foil prints a neutral grey.** `press.py` is the staged model — ink limit → linearization → grey balance → colour transform, each fitted on what the ones before it could not remove — and it beats the single polynomial it replaced on every press × scanner the harness has: matte/honest 2.22 → **1.34**, matte/biased 4.99 → **3.87**, holo/honest 4.98 → **3.64**, holo/biased 10.05 → **6.42** ΔE00. Each stage measurably reduces the next one's residual (linearization 23.30 → 6.34, grey balance → 3.03, colour → 2.68). On the blue sticker through an honest scanner a grey ramp comes off with **no visible cast**; what a biased one leaves is the reference of §1.1, which is stage 8 and says so
- [x] **The blocker: a survey round could not be stored.** Every patch array was validated against one global chart length, so a 468-patch round was written and read back as *unreadable* — a verb whose output the loader discards. `ChartId` is the closed set of targets code names, `Round.chart` records which one, and validation is against the chart the round itself names. A `Pending` records **what went on the paper** rather than letting `calibrate add` recompute it: a survey prints uncorrected while a check prints through the model, the model moves the moment a round is added, and the aim moves with the intent
- [x] **`Profile.gamut` is a `Gamut` solid, not a mask over one chart's patches** — a profile has one gamut but its rounds no longer share a patch set, so a boolean array of one length cannot answer for the other
- [x] **Gamut compression only fired when the *send* overflowed.** A degree-2 transform extrapolating past the region it was fitted over returns a perfectly in-range send for a colour the paper cannot make: measured on the simulated sticker, a wanted dark orange went out as (21, 66, 95) — heavy ink for a light colour — and came back **blue** at ΔE00 63.6. Reachability is two questions now (`PressModel.fits`), and the model carries the region it was measured over
- [x] **The lightness give-up guessed one direction** — inferred from which end the *send* overflowed, which says nothing about a colour whose send is in range. On a medium whose white is L* 74 that pushed such colours further outside every time; both directions are tried and the smaller move wins
- [x] **The reported cast contradicted the print.** It averaged in neutrals the medium cannot make, and the ramp is L*-spaced from 2 to 98 on purpose so its ends clip to the ink floor and carry *that* hue: a* +5.10 (red) reported where the printable neutrals read a* +0.86 (neutral). Masked by the same reachability the error is
- [x] **`Substrate.json` never served `measured`**, so the print screen read `undefined` as false and printed "Not measured" over a paper the CLI was reporting as (151, 189, 203) on the same profile. A derived property a reader has to re-derive is one two readers will disagree about
- [x] **A verification round is a `Purpose`, not a chart id** — a refinement round and a check print the same small chart, and what differs is what is done with the answer. A check is scored and kept **out** of the fit, because a model that trains on its own exam cannot fail it, and `plateau` is judged on the checks once there are any. Measured: a model fitted on one press verifies at 1.6 on that press and **18.4** on another
- [x] **Adaptive placement moves only the lattice** (`calibrate.adaptive`, the `targen -c` mechanism) — the greys, the ramps and the substrate stay put, so two checks remain comparable on everything a trend is read from. Deterministic, or two verification errors are not comparable
- [x] **`Reference` is the ColorChecker and deliberately not IT8.7/2** — an IT8's 264 patches are batch-specific and ship with a data file per run, so hardcoding "the" values would be inventing a measurement. Its published values are D50/2° and everything here is D65, so they are Bradford-adapted: that moves the chart's **blue** 4.82 ΔE00 and its white 0.16, which is precisely the region a blue substrate is the whole discussion about
- [x] **`Sender` is a protocol, and the compression is one function** (`calibrate.compress(raw, arr, fits=)`) — two things ask for a send now, and compression living on one of them is a second implementation waiting to happen on the other
- [ ] **The foil profile still has to be re-measured on real paper.** Everything above is measured on a simulator anchored to the real profile's own substrate reading, which is the right way to choose between models and is *not* a print. `holo-plain`'s four stored rounds stay in the file as the record of the defect (`Profile.unreadable` counts them), and the first real survey on that stock is what makes the medium printable
- [ ] **`profile strip` and `profile preview` still go through the hand-set recipe alone**, which is right for the by-hand route and now inconsistent with a measured profile: `Profile.render` funnels aim → model → compression, and a *strip* of that would vary the intent rather than a multiplier. Worth having as `profile strip --vary intent` once somebody has judged one on paper

- [x] **Existing profiles are re-measured, not migrated — decided.** A stored round's `sent` was chosen by the method being replaced (`holo-plain`'s rounds 2–4 were printed through a correction already driving toward yellow), on a patch set with no substrate reading, no per-channel ramps and a neutral ramp in the wrong units. Refitting them better is fitting a better model to evidence gathered for a worse one. `Profile.unreadable` already counts a round whose shape no longer matches, so no migration code and nothing deleted silently — the four rounds stay in the file as the record of the defect
- [x] **The loop shape changes: one survey, one verification, refinement optional.** Six-rounds-on-a-sheet existed only because 80 patches cannot characterize anything. Survey (one sheet, ~457 patches) → `calibrate verify`, which prints what the model *predicts* and scores where it landed — **the first number in the system that can fail**, and the absence of which is why §1.2 went unnoticed. `plateau` judged on that, not on the fit's own residual
- [x] **Survey density is a setting, because a sheet of holographic sticker is not free** — `full` (7³ lattice, ~457), `half` (5³, ~215), `quarter` (4³, ~150). The ramps, neutral ramp, substrate and max-ink patches are identical at every size; only the interior lattice shrinks, since the others are what linearization, grey balance and the substrate term are built from
- [x] **A patch carries its `Role`** (`substrate`/`ramp_r`/`ramp_g`/`ramp_b`/`neutral`/`max_ink`/`repeat`/`lattice`), so every stage selects by role rather than index arithmetic — `_GREYS = slice(0, 16)` is exactly the implicit index a chart change breaks in silence

- [x] **CONFIRMED ON THE REAL `holo-plain` PROFILE, and the loop was *diverging* while reporting progress.** The substrate scans **(144, 189, 208)** — blue **+64** above red — and its influence is coverage-dependent: +57.75 B−R in the highlights against +5.50 in the shadows (ink covers it where it is dark, it shows through where it is light). Aiming at an absolute neutral, the fit fought it and pushed harder every round: the blue-minus-red of what it *sent* for a neutral went **0 → −28.33 → −30.75 → −32.42** over four rounds — monotonically more yellow ink — while the reported L\* error *fell* from −12.73 to −4.90, so `plateau` would have certified it. Today it sends a mid-grey as **(232, 189, 166)** and a 200-grey as **(255, 255, 217)**: R and G pinned at the ceiling with B below them **is** the yellow cast, produced by the per-channel clip. **48 of 80** patches clip
- [x] **Aiming relative to the substrate fixes it, measured on that same stored data** — mid-grey sent (232, 189, 166) → **(139.5, 137.5, 144.4)**, the ramp's B−R tilt −34.23 → **+2.06**, clipping 48/80 → **5/80**. Nothing new printed or scanned: it re-fits the rounds already on disk
- [x] **Unprinted paper is three free measurements and the chart is already covered in it** (white gutters and margins): (a) the **substrate colour**, which is what relative aiming needs and is truer than patch 15, since that one is printed at 252 rather than bare; (b) a **per-round white** to put every round in the same scanner state — drift across the four rounds is **9 levels / 6%**, currently pooled as identical, though normalising alone moved the tilt only −34.23 → −33.61, so it is second-order here rather than the cause; (c) a **per-position white across the sheet**, the only handle on the flatbed's ΔE-5 centre-to-edge non-uniformity
- [x] **The substrate belongs in the model as its own term, not something the polynomial infers** — show-through is coverage-weighted (Murray-Davies / Kubelka-Munk), which is exactly the +57-vs-+5 gradient above, and a degree-2 RGB polynomial can only approximate it by bending the whole response
- [x] **Offer partial adaptation, not just relative-vs-absolute** — relative aiming means a card's white prints as the sticker's blue-white, which is the honest answer on a blue substrate and what the eye adapts to; wanting *some* of it neutralised is a legitimate preference and is what a perceptual intent does. A 0..1 knob, defaulting to fully relative

- [x] **THE ROOT CAUSE: the correction's input space is *scanner RGB* and it is applied to *sRGB card pixels*.** `fit(scanned, sent)` learns scanner-reading → send, and `Correction.apply_to_image` feeds it image values. Nothing establishes that those are the same space, and they are not. So the loop converges — correctly — on "the print **scans as** the target's numbers", which is the documented guarantee of the **closed-loop / scan-back** method (Ostromoukhov et al., SPIE 2170, 1994): accurate *only* for input having the same ink and halftone characteristics as the calibration patches. A Scryfall PNG is not that. On matte a decent scanner is near enough to sRGB that the two objectives nearly coincide; on foil they diverge, and the divergence **is** the yellow. Measured floor for the assumption: patches with identical scanned RGB can differ by **ΔE 10** in CIELAB, and identical Lab can give quite different RGB — a flatbed's sensitivities are not a linear transform of the CIE matching curves
- [x] **So the fix is to name the missing transform, not to tune the fit.** A `Reference` stage (scanner reading → reference space), identity by default **and loudly labelled as an assumption**, fillable from an IT8.7/2 or ColorChecker read. Everything else valid without it: relative-to-media-white aiming, grey-axis priority, gamut compression, ΔE00 scoring, gamut from scans. Without a reference the accuracy floor stays and should be *reported*, not hidden by a residual that only measures scanner agreement
- [x] **Aim relative to media white, and do *not* compensate the black point** — measured, scanner-free: relative aiming cancels the scanner's per-channel *gain* (paper and patch both pass through it) and collapses the grey cast in every scanner case (foil real-case greys a\* +2.26 / b\* −3.01 → **+0.48 / +0.36**; matte honest-scanner ΔE 3.95 → **1.04**). Black-point compensation was tried and is **harmful** here — it lifts the whole shadow end and roughly doubles ΔE (foil 7.56 → 16.92). The scanner's *offset* term (flare, specular pedestal) does not cancel and needs a reference
- [x] **Two hypotheses tested and rejected, do not build them** — the fitted polynomial is **monotone** (0 reversing steps on the neutral, red and blue axes, both presses), so it is not causing banding; and **scrambling the patch layout** the way `printtarg` does changes nothing (flare error on the greys 10.54 → 10.43 levels, ΔE slightly worse), because every patch is already surrounded by a white gutter, which is what makes flare near-uniform and is why relative aiming works at all
- [x] **The literature's own numbers, for calibrating scope** — printer-only calibration with a real spectrophotometer, 9×9×9 = 729 patches, Delaunay tetrahedra + trilinear interpolation: mean **ΔE 1.6, σ 0.7**. That is the ceiling. Also from the same paper: a flatbed's readings vary by up to **ΔE 5** between the centre and the edge of its window (scan the middle only), the neighbourhood measurably contaminates a reading, and ink from successive cartridges varies enough that a profile has a shelf life worth recording in its notes
- [x] **Grey density is a literature recommendation, not just an intuition** — "tetrahedrons defined by vertices lying on different sides of the gray axis may be responsible for considerable errors… diminished by densely populating areas close to the gray axis". Ours is 16 neutral patches against 64 colour ones
- [x] **The chart has no per-channel ramps at all** — a neutral ramp and an interior lattice, so R, G and B *cannot* be linearized separately, which is step two of every industry workflow (ink limit → linearization → grey balance → colour transform). QTR's flatbed method starts by finding the ink limit off a 21-step single-channel wedge for exactly this reason
- [x] **The neutral ramp is `linspace(4, 252)` in device code values**, so after a printer's tone response the visual steps are badly uneven and the highlights — where the eye is most critical — are undersampled. Should be spaced in L\*
- [x] **More patches is the wrong lever; bigger patches measured twice is the right one.** IT8.7/3 is 928 and IT8.7/4 is 1617 for instrument-read targets, but the trade's own advice for a scanner is "lower patch count and measure twice, or make the patches wider" — which is what proxdex's own 228-worse-than-80 measurement already found. So: fewer, larger patches, and `targen -c`-style **adaptive** placement inside the measured gamut for round 2+ (ArgyllCMS's OFPS raises adaptation from 0.1 to 1.0 once a prior profile exists) rather than a fixed lattice that spends 43 of 80 patches on colours foil cannot make
- [x] **The scanner is not a colorimeter, and on a specular substrate it is not even close** — nothing in proxdex characterizes it, so its response is baked into every correction. Simulated: on foil the current loop leaves ΔE 9.56 and greys at b\* **+8.66** (visibly yellow); granting the fit the scanner's own response takes it to ΔE **1.61** and b\* +3.59. The single biggest cause, ~5 of the ~8.7 units of yellow
- [x] **No white point anywhere** — the target is absolute sRGB, so a warm stock's unreachable neutral white makes the fit fight the paper and distort the midtones with it. Judged after adaptation to the paper white (how you see a sheet in your hand), the absolute aim leaves greys at a\* +4.10 / b\* −9.81 against **a\* +0.55 / b\* −1.16** aiming relative to media white
- [x] **The chart does not fit the medium** — on foil **43 of 80** round-2 sends clip and only 37 patches are reachable, and `usable()` then drops them, leaving 37 samples for a 10-term × 3 model. Round 1 drops nothing (its sends *are* the target), so the first and most influential fit is trained on 43 patches that measure nothing
- [x] **Per-channel clipping in `Correction.apply` shifts hue, and toward yellow exactly where it hurts** — the highlight wanted send (273, 264, 299) and got (255, 255, 255): 44 of blue refused against 18 of red, so a warm stock's highlights print at the paper's own yellow. A gamut compression toward the neutral axis is the fix, not a per-channel clamp
- [x] **Grey has no priority** — 16 of 80 patches are neutral, so the axis the eye judges is outvoted 4:1 by colour patches. Weighting it helped where the upstream was sound (matte 0.79 → 0.73 ΔE) and could not touch foil
- [x] **The score cannot see a cast** — Euclidean RGB over the reachable set, so a grey b\* of +8.66 does not move the number the loop watches. Should be ΔE00 in Lab
- [x] **Within-patch spread is measured and thrown away** — `sample_patches` takes the median and keeps nothing, but a specular/holo substrate speckles, and the spread is the honest signal that a reading is not a measurement
- [ ] **A hologram is gonioapparent** — its colour depends on illumination and view angle, so a single flatbed geometry cannot measure it at all (industry uses multi-angle or sphere instruments). A scan loop on holo foil should say so rather than fit a confident polynomial; the honest route there is a hand-set `Recipe` judged off `profile strip`
- [x] **Order of operations is not the industry one** — one degree-2 polynomial does tone response, grey balance and colour matrix at once. Best practice is ink limit → linearization → grey balance → colour transform, each stage monotone and inspectable
- [x] Releasing is one command (`scripts/release.sh`), the tag message is the release notes, and `Release` re-checks the gate + tag/version match before publishing
- [x] GitHub releases exist for every tag (v0.1.0 … v0.5.0), with the artifacts attached — v0.5.0 rebuilt from its tag matched PyPI's sha256

Four faults: `renderAlignPanel` read `g.frameless` on a **null** guide and threw, taking the panel *and* the `Align the border` button with it; `whyThisSpec` returned '' when nothing resolved, so the one card needing an explanation got silence; a step setting lived only in the DOM, so clicking `Align the border` (a re-render) reverted the Frame to Automatic — now `stepMem`, keyed by card/side/step so an override cannot leak onto the next card; and `onSetting` returned early with the layer down, so a **done** step ignored the Frame entirely. Verified end to end: choose → align → run → `Keep`, and the card resolves via pin with `frames check` clean
- [x] **Picking between two borders is a radio group now** — it was a via chip beside a mono id plus a row of same-weight buttons for the others, which showed neither which spec was in force nor what it was *called* (the buttons had the names, the selected one had only its id). One row per applicable spec, each with its **four border widths** (`3.12 / 3.24 / 6.76 / 7.16` vs `9.10 / 2.61 / 6.76 / 7.16` is the difference at a glance; `Candidate.json` serves `mm`, and `FrameGuide.json` deliberately does not since it is also the on-disk format), the whole row as the hit area, arrow-key navigation, the accent on the selected row as everywhere else in the app, **sorted by id** so the row you click does not jump to the top, and no selection styling at all when only one applies
- [ ] The align panel cannot name **what a done master was actually fitted to** — `.fit-bordered` records it and `/api/frame` does not serve it, so a card whose printing resolves to nothing shows `no frame spec measured` over a master that was bordered against a real spec, and picking a different candidate on a bordered card says nothing about the master going stale (`doctor`'s `stale-spec` knows)
- [ ] The border step's **Frame** dropdown offers every spec of **both games** (`mtg-vanguard` on a Pokémon card) and labels them by bare id rather than name — `/api/frame` already filters by game (`reg.choices(card.game)`), the step schema from `/api/meta` does not
- [x] **A square promo border** — `pokemon-ex-plain`, one hand reading (554×769, **23px on all four edges**), covering set `np` alongside the strip spec: the promos printed without an e-Reader dot code have nothing to be asymmetric about. Top 2.991% / sides 4.152% — 2.66 / 2.64mm, the thinnest Pokémon spec and nearer `mtg-m15` than WOTC. Square in mm as well as px, which is a separate fact (different fractions, one width) — the 0.02mm gap is the file's aspect being 0.85% wide of the card's. Both `np` frames resolve as candidates since nothing in the metadata says which a card is; `pokemon-ecard-ex` is the default on weight of evidence (two cards vs one), **not** a claim about which is commoner
- [x] **The ex era's strip moved** — `pokemon-ecard-ex`, from two hand readings (747×1040: L32 R27 T39 B71; 455×642: L20 R17 T23 B43), covering set `np` only. The e-Reader dot code runs along the **bottom alone** (6.01mm) with three ordinary edges (top 3.26 / left 2.76 / right 2.33mm), so it is a different _shape_ rather than a renumbered `pokemon-ecard` — that spec would have asked 7.16mm of left border where the card has 2.76. Stored as the per-edge average; the two cards agree to 0.17pp across a 1.64× scale gap and the stated totals land exactly on three of four (the fourth is a 1px slip, 0.14mm). **Left and right not collapsed** — both cards read left wider by the same 0.67pp, which a cutting error does not do. Keyed to `np` alone: the strip ran on into ex, but that has not been read
- [x] **A second e-Card frame** — `pokemon-ecard-deep-top`, from a third hand reading (468×650: L52 R20 T67 B49). Which printing has the deeper top is **not** recorded, because it was not read

## Speed and waiting

- [x] **Browse was slow because of provider art, not JSON** — the set list answers in 9ms warm, then the page pulled 174 logo PNGs at ~139 KB each (24.7 MB) into a slot 2.25rem tall, and a 60-card page pulled 45 MB of full-size scans into 190px tiles, all of it again next visit. `art.py` + `/api/art`: fetched once, resized to the size it is drawn at, kept in the cache dir, served immutable. **4.17 MB → 215 KB** for the first screenful of logos, **45.1 MB → 2.10 MB** for a card page, **0 bytes / 0ms** on the second visit
- [x] A picture host is not an API (`net.CDN_INTERVAL`) — held at the 100ms Scryfall asks of _its API_, one screen of 174 logos would have been 17s of pure waiting. `get` takes an `interval=` and the limit on art reads is the pool that issues them
- [x] The host is checked against a list, full-host match — a lookalike domain and the allowed host as a path segment are both refused, and pinned. An open fetcher is a hole even on localhost
- [x] **Waiting has a shape** — `progress.py`, a file channel (`$PROXDEX_PROGRESS`) that is a no-op for a terminal user, so the CLI's output is byte-for-byte what it was and nothing is parsed out of human text. `_each` reports items, `sheet._pages_to_pdf` reports pages; `/api/progress` reads it while `run_cli` is still blocking. Measured: a 47s duplex imposition went from one spinner to `3 of 4 · page 3`
- [x] An unknown total stays unknown — one card through Upscayl has no fraction to be had, so it gets a sweep, an elapsed clock and `~41s typical` (the median of _your own_ last runs, labelled). Never a bar position: a fraction nobody measured sitting at 90% is the same lie as a border nobody measured
- [x] **A count of one is not a position** (`Report.positional`) — one card through Upscayl or grade is a real count of 1 whose bar could only read 0% and then vanish, which is what "the bar is empty and then it's done" was. Below two items a reader falls back to the sweep, the clock and the typical; the rule is on `Report` because both readers need the same one
- [x] **An item names itself** — `cli._each` took `str(item)`, so the three verbs whose items are `Card`s put `Card(id='ecard3-141', dir=PosixPath('/Users/…` in the panel as the note _and_ in `_last_failed`, where a retry needs a bare id. `name` is now a required parameter: a forgotten one is a type error
- [x] **`~14s left`, measured** (`Report.remaining`) — the command's own elapsed over the items it really finished, timed from when the _counting_ began (`Report.started`) rather than process launch, which was charging 5.2s of interpreter startup to the first page. Silent before the first item, at a total of one, and **once the count is complete**: `sheet` embeds the PDF after its last page, and `0s left` under a full bar through that is the spinner-that-knows-nothing with more confidence
- [x] Only runs the remembered estimate is _shown_ for are recorded, so one card through Upscayl and forty of them stop pooling into a median describing neither; well past it the panel says `longer than usual`
- [x] A wait too short to be one gets no panel — held back 320ms while the top sweep acknowledges the click, so a 20ms skip or config set no longer flashes a modal. The note is one line, truncated, full text on its `title`
- [x] `--clear-cache` clears _both_ kinds — `net._CACHED` is one list, or a second kind of cached thing becomes quietly unclearable. `where` counts the pictures held
- [x] Skeleton plates on the browse and search pictures, which had none: the tiles sat empty rather than loading
- [x] **A Pokémon tile takes the provider's own small scan** (`[sources] scrydex_thumb_url`, `/small`) — 245px and ~30 KB against `/large`'s 825 KB. The art cache could shrink what the _browser_ pulled but not the fetch that fills it, so the first visit stayed slow: a cold 60-card page went **3.49s → 0.72s**. A separate `SearchResult.thumb_url` rather than a suffix swapped at the point of use, so nothing downstream can file a 245px master — which would border, upscale, grade and impose without complaint and be wrong only on paper
- [x] **MTG too** — `image_uris.normal` (488×680) for the tile, `png` still what gets filed. The mechanism differs because the providers do: Pokémon's variant is a URL template (configurable), Scryfall's is a key on the card's own response (`_MTG_THUMB_KEYS`, not a setting — there is no template to point). Measured over 32 cards in four sets: `png` 1657 KB median (range **331-2206** — an old scan is far heavier than a modern one), `normal` 120 KB (range 78-146). ~14x at the median, 3x on the lightest set, and the real win is a **flat** cost: a page of Alpha now costs what a page of Aetherdrift costs, where before it was 102 MB against 23. A cold 60-card MTG page is 1.11s

- [x] **Pokémon name search was one term per word, which threw the words away** — a space separates *terms*, so `Moo Moo` became `name:*Moo* name:*Moo*`: two identical substring tests, exactly equivalent to searching `Moo`, answering Amoonguss / Bloodmoon Ursaluna / Roaring Moon with no Moo Moo Milk in sight. Joined into `name:*Moo*Moo*` it returns the five that exist — and the wildcard where a space was typed is also what matches **Moo-Moo Milk** (Neo) *and* **Moomoo Milk** (HeartGold), neither of which `name:"Moo Moo"` finds at all (0 results, measured). Scryfall stays per-word; it already ranks correctly and is order-insensitive

- [x] **An empty search names what emptied it** — `state.find` survives paging, a screen switch and a reload, so the filter that killed a query is usually one set on another screen a while ago: browse a set, switch to Search, type a name, and the set is still narrowing. `Nothing matched. Try fewer filters` was true and useless; it now reads `Nothing in Pokémon matched Moo Moo with set base1` and carries a **Drop it** button
- [x] Scryfall stays **per-word**, measured rather than assumed: the phrase form `name:"Serra Angel"` is more precise (1 hit vs 2) but `name:"kiki jiki"` returns **0** where `name:"Kiki" name:"Jiki"` finds Kiki-Jiki — it breaks on the hyphens Magic names carry, which is the same hazard the Pokémon join fixes. Its one real flaw is that repeated words collapse (`Moo Moo` = `Moo`, 138 cards), and no Scryfall spelling avoids that without the hyphen regression

## Robustness

- [x] **Retries are chosen by what giving up costs** — `net.get(attempts=)`, default 4 for reads that draw a screen, `PATIENT_ATTEMPTS` = 7 for a card's metadata and its image. Takes the loss from ~1 card in 16 to ~1 in 1000 at the measured 500 rate; the 23.5s worst case is spent only when a host really is down, and a stale cache entry is still served before it raises
- [x] **A card is filed from metadata the caller already read**, so the UI's Add no longer re-asks for the name/set/rarity it had just drawn — `fetch --name/--set-name/--rarity/--subtypes`, `FetchBody.known`, one CLI call per described card. Pokémon only: a Magic image URL is a uuid path only Scryfall's answer carries. Safe _because_ `download` refuses the placeholder — skipping the lookup skips the proof the id exists
- [x] A Pokémon search row now carries the traits a lookup does (`subtypes` added to `select`, 5% of response size) — a card added from a search used to get **no** traits while the same card via `fetch` got rarity and subtypes, so a subtype rule answered differently depending on which verb filed it
- [x] **A failed download no longer leaves a phantom card.** The folder plus `.game`/`.layout` with no image counted in `ls`, drew a contact-sheet tile and read "4 of 5 originals" — a card that could never become ready. `_acquire` rolls back a folder it created when nothing landed; an existing card whose re-download fails is left alone
- [x] **A fetch failure names the card, and `fetch` prints the retry.** `NetworkError`'s message is the _host_, so a batch reported `SKIPPED api.pokemontcg.io` and you could not tell which card to run again; `_get` takes a `what=` now and `fetch` ends with a paste-able `proxdex fetch --game … <ids>` for exactly what missed
- [x] **The image host answers 200 with a placeholder for an id it does not have** (`base1-999`, `zzzz-1` → the same grey file), which is why a Pokémon fetch must resolve the id against the metadata API even though the image URL is derivable from the id alone. `sources.is_placeholder` (640×892, palette mode — no real scan is either) refuses it instead of filing a grey rectangle that every later stage would happily print
